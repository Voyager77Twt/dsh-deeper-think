# 闪电插件部件说明书

> 目标：在没有快速判定标准（无 oracle）的问题上，用 ≤3× 的 token 换取更全面、可核验的回答，并确保模型真的执行了检查，而不是口头宣称。
>
> 本文按"每个部件是什么 → 为什么这样干 → 如何确保执行"的结构写。

---

## 0. 总图

```
┌─────────────┐   POST /dsh-deeper-think/set   ┌──────────────────────────┐
│ 客户端按钮   │ ─────────────────────────────> │ 宿主 index.js            │
│ client.js   │   {sessionId, on}              │  seats / turnOn 账本     │
└─────────────┘                                └──────────┬───────────────┘
                                                          │ 每步注入纪律卡
                                                          ▼
                                               ┌──────────────────────────┐
                                               │ 模型（按七步产出 json 块）│
                                               └──────────┬───────────────┘
                                                          │ step/end 抽块
                                                          ▼
                                    ┌──────────────────────────────────┐
                                    │ 宿主 v5.js                        │
                                    │ 临时 v5.json → v5check.py（29 条；常见 25–27）│
                                    └──────────┬───────────────────────┘
                                               │ 失败码
                                               ▼
                                    同回合注入修正 → 模型返工
```

## 0.5 检索判断与深度（0.1.11+）

- 模型第一行写 `SEARCH_PLAN`（need/mode/budget/depth/why）；
- 设置页 → 更深思考 → 搜索：判断方式（自动/严格）、每回合上限、自定义触发词（命中提示一次）；
- 机械词表只提示：首次动手、词表命中、写新文件/改依赖、未知专名；
- `research-first`：宿主观测到真实搜索调用前拦 `write/edit`；`build-first`：不拦，写后提醒；
- 深度阶梯：orientation → targeted → cross-check → gap → saturation；每条账本写 `not_covered`；
- 预算：保底 1 次、默认天花板 8、模型自报、到 80% 只提醒；
- 限制：宿主不代搜、不验摘录；build-first 不能强制补搜。

## 1. 客户端按钮（lib/client.js）

**是什么**：挂在 composer 模型选择器左侧的闪电按钮。

**做什么**：

- 维护每个会话的开/关状态（`keyOf(sid)`）；
- 点击只改 DOM 属性（`data-on`、`aria-pressed`、`title`），不触发 React 重渲染；
- 把状态 POST 给宿主（`/dsh-deeper-think/set`）；
- 空心/实心、文字「消耗更多token」、悬停提示。

**为什么这样干**：

- 用 DOM 直改而不是 `useState`，是因为重渲染会重建组件、累积监听器，造成卡顿与状态错位；
- 按会话存，是因为"深想"是单次对话的选择，不是全局开关。

**如何确保**：冒烟测试 11 项（空心/实心规则、文字、白底、提示语、按会话隔离、状态驱动）。

---

## 2. 宿主状态通道（lib/index.js）

**是什么**：本地 HTTP 路由 `/dsh-deeper-think`（RPC 因 cordis 注入限制不可用，已由 HTTP 替代）。

**做什么**：接收 `{sessionId, on}`，写进内存 `seats`；按会话隔离，另设 `__global__` 兜底（用于批量/测试）。

**为什么这样干**：模型进程与浏览器是两套环境，必须有一条真实通道把"用户点了开关"送达宿主；写文件或改配置都太重且易被覆盖。

**如何确保**：读回响应 `{"ok":true,"on":...}`；宿主日志记录每次 set。

---

## 3. 回合快照（turnOn）

**是什么**：`turn/start` 时把当前 `seats` 值抄进 `turnOn`。

**做什么**：本回合内所有注入、拦截都读 `turnOn`，不读实时 `seats`。

**为什么这样干**：防止"做到一半误关开关"导致本轮协议断裂；关掉只应影响下一轮。

**如何确保**：单测覆盖"中途关闭后本轮仍注入、下一轮停止"。

---

## 4. 每步纪律卡（agent/pre-step）

**是什么**：每步开始前追加一条 `source.kind = dsh-deeper-think` 的用户消息，约 300–500 token。

**做什么**：

- 七步流程：A1 需求点 → M1 参照 → S1 边界 → S2 表外三问 → S3 判据 → S4 产物 → S5 演示 → S6 修复 → S7 未覆盖；
- 三条必要条件：清点 / 变质 / 一致；
- 块格式骨架与字段规则；
- 成本纪律（小数据不写脚本、演示 ≤3、正文 ≤120 行）。

**为什么这样干**：

- 模型缺的不是能力，是"何时停"的判据；卡片把停止条件从"看起来对"换成"清单结清"；
- 只贴短卡、不贴整份文档，这是 token 便宜的关键。

**如何确保**：注入消息带 `source.kind`，可在会话日志中核对；v5.js 在 seat 开启时每步注入。

---

## 5. 留痕文件禁令（tools/pre-execute）

**是什么**：拦截 `boundary.md / criteria.md / pre.md / acceptance.md / demo_runs.txt / settle.md` 的写入。

**做什么**：返回 `{kind:'deny', reason:'v5 模式不建留痕文件…'}`；产物（answer.md、代码、图）放行。

**为什么这样干**：v4 的六个文件要写、读、再检查，是 token 大户；v5 把留痕压进回答里的一个 json 块。

**如何确保**：拒绝理由固定可检索；`{"na":...}` 机制保证"确实做不到"时能写明原因而不是硬造。

---

## 6. 写后提示（tools/post-execute）

**是什么**：成功写入产物后，下一步注入"补 demos/uncovered/repair"。

**做什么**：先 `await next()`，再判 `result.isError`：失败/被拒 → 不提示；成功 → 记待办。

**为什么这样干**：被拒还提示"已写出"是假汇报；反欺骗要求没发生的事不能说发生。

**如何确保**：单测覆盖"被拒不提示、成功才提示"。

---

## 7. 块抽取与临时校验（step/end + v5check）

**是什么**：

- 从本步回答正文抽取 ```` ```json ... ``` ```` 块；
- 写入 `%TEMP%\dsh-deeper-think-v5-*.json`（不落工作区）；
- `spawnSync` 调用 `v5check.py`，超时 8 秒；
- 解析 `--json` 输出，取失败码。

**做什么**：25 条规则，覆盖五组：

| 组 | 规则 | 含义 |
|---|---|---|
| 边界 | B1/B2/B3 | 八维≥6、歧义≥1、扩展维度有理由 |
| 必要条件 | A3-1/A5-1/A4-1 | 清点/变质/一致三节必须给出（或 `na`+原因） |
| 判据 | T1/T4/TOL/V1/T3/INV1/KIND1 | 引用实体、来源含数字、容差不超限、演示覆盖、kind 合法、三类覆盖≥2 |
| 演示 | N1/N2/N3/DE1 | FAIL 具体输出、崩溃不算、复原、actual 具体 |
| 诚实与顺序 | CE1/ORD1/CH1/SR1/SS1/S1/X1/R5 | 声称有事件、判据先于产物、无空转、来源形状、不许自评、首轮全绿≥3 演示、表外三问、可修必修 |

**为什么这样干**：

- 只有"能失败"的检查才能把"看起来对"变成"清单结清"；
- 结构化块让检查变成机械比对，不依赖人读；
- 不落文件避免 v4 的重复读写成本。

**如何确保**：合规样例 25/25 通过；旧块（缺三节）20/25 失败；改坏判据/演示会触发对应码。

---

## 8. 同回合修正（pending → 下一步 pre-step）

**是什么**：失败码写进 `pending`，下一步注入 `⚠ 本步骤结构化块未通过：… 本轮结束前必须修正`。

**做什么**：把"下一步改"压缩到"本轮内改"，避免问题拖到用户看到最终答案之后。

**为什么这样干**：DSH 未暴露"拦截助手消息"的钩子，无法在草稿显示前拦截；只能在下一步把错误指出来，逼模型返工。

**如何确保**：0.1.5 起实测：空 boundary 块在同一回合收到 `B1,B2,T1` 警告。

---

## 9. 回合末兜底（turn/end）

**是什么**：若整轮没有块或仍失败，把结论存入 `pending`，下一轮开头注入。

**做什么**：通过 → `v5check：25/25 通过`；缺块 → `未找到结构化块`。

**为什么这样干**：保证每个回合都有可查的验收记录，而不是"没消息就是通过"。

---

## 10. 检查器的边界（诚实清单）

| 管不了 | 原因 |
|---|---|
| 草稿先显示 | 无拦截助手消息的钩子 |
| 模型不写块 | 提醒是强约束不是强制；会记失败码但块仍由模型生成 |
| 块外叙述是否真 | 检查器只读块 |
| 宿主复跑演示 | 未实现（需 SP1/RERUN 类能力） |
| 无 Python 环境 | 检查器跳过，退回文件齐全式提示 |

---

## 11. 成本模型

- 每步纪律卡 ≈ 300–500 token；
- 无留痕文件：省去 6 个文件的写、读、复读；
- 演示 ≤3、批量跑一次：省去反复执行；
- 目标 ≤3× 基線；实测：微任务 2.25×（0.1.5），重型做法 6.6×（0.1.6 前），0.1.7 的成本纪律用于压后者。

---

## 12. 一句话

插件不是"教模型更聪明"，而是**把停止条件从"看起来对"换成"清单结清"**，并用一个**能失败**的检查器和**同回合返工**保证它真的结清了。

## 13. 理论依据（不重复造轮子）

插件的三类检查不是自创，分别对应三个成熟方向：

| 论文/方向 | 核心结论 | 插件里的对应 |
|---|---|---|
| Chen, Cheung, Yiu 1998《Metamorphic testing: a new approach for generating next test cases》；Segura et al. 2016《A Survey on Metamorphic Testing》(IEEE TSE, https://doi.org/10.1109/TSE.2016.2532875) | 没有 oracle 时，用"变换 T 下关系 R 必须成立"来证伪 | `invariants` 字段与 A5-1 规则 |
| Jia & Harman 2011《An Analysis and Survey of the Development of Mutation Testing》(IEEE TSE, https://doi.org/10.1109/TSE.2010.62) | 变异体能检验"检查器是否真的能失败" | `demos` 的"改坏→必须 FAIL"、N1/N2/N3/DE1 |
| Huang et al. 2023《Large Language Models Cannot Self-Correct Reasoning Yet》(ICLR 2024, https://arxiv.org/abs/2310.01798) | 无外部反馈时，模型自我纠错不可靠，甚至变差 | 外部 v5check + 同回合修正注入，而不是让模型自查 |
| Stechly et al. 2023《GPT-4 Doesn't Know It's Wrong》(https://arxiv.org/abs/2310.12397) | 迭代自我批评不能可靠发现错误 | 宿主记录失败码、下一轮强制带着失败码继续，而不是问"你确定吗" |
| Weng et al. 2022《Large Language Models are Better Reasoners with Self-Verification》(EMNLP 2023 Findings, https://arxiv.org/abs/2212.09561) | 把结论当作条件做反向验证，可提升推理 | 结构化块要求给出 ref/source/tol 与演示，等价于可解释的验证问题 |

结论：插件把"变质测试 + 变异测试 + 外部反馈"这三项已有方法组合成一条低成本流水线；没有另造一套验证理论。
